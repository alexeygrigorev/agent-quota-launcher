# Quota-aware agent launcher: decisions and acceptance

Observed 2026-10-04, Europe/Berlin. Owner: desktop Astra design/challenger; native implementation head: `quota-launcher-head`, workspace `/home/alexey/git/agent-quota-launcher`, aplexer UUID `6be4c247-4410-4bdb-968e-7fc2d5844941`. This note is a design/verification ledger, not a claim all described features are implemented.

## Product boundary and useful first consumer

A project head submits a concrete owned task. A small Python/SQLite launcher validates capacity, chooses an eligible provider, starts a native aplexer worker and records an outcome for review. The new Agent Dashboard should consume a private projection of these facts. `quse` remains the quota source; aplexer remains the session/messaging layer. Existing collectors/supervision stay running. The implementation head delegated core code/tests to `quota-launcher-core`; an independent Antigravity reviewer owns `reviews/`.

Challenge to the user's framing: maximizing used allowance is a bad objective when task ownership, task fit or deliverable quality is missing. Reset timing is a secondary preference among useful eligible tasks. A launch which spends quota and creates no accepted result is a negative outcome. More workers is useful only when their tasks are independent and the host can admit them. A fixed worker count is unnecessary.

Scope challenge: a new general agent framework would delay the first useful run. Build bounded admission plus two working provider adapters first. Adapter/plugin machinery, cross-host scheduling and unsupported promotional adapters remain explicit follow-ups. The smallest acceptance is one head-owned task submitted, admitted, genuinely run, incrementally written, reviewed and reproducibly restored from the independent backup.

## Architecture source and what was adopted

[Heru README](https://github.com/alexeygrigorev/heru), read 2026-10-04, describes engine adapters separated from launch profiles, structured invocations, a normalized event envelope, continuation IDs, and contract tests. It sends quota reporting to quse. These are architecture ideas only; no Heru code was copied, installed or built. Keep the launcher above those seams: measurement, scheduling/admission and native execution have different responsibilities. Preserve native engine/requested model/observed model independently rather than hiding aliases behind a universal provider name. Do not claim a uniform resume implementation until each provider's actual continuation has been tested.

## Eligibility before ranking

1. Task has a stable idempotency key, owner/head, goal, task type, canonical cwd, bounded exclusive paths, timeout, first action and deliverable contract. Idempotency key reused with different payload fails. Reject parent/child path overlap with live or unreconciled reservations. Symlink resolution reduces accidental overlap but is not a security sandbox against the same Unix user changing links later.
2. Exact route is supported and entitled. Store executable/version, requested model, subscription route, authoritative source, observation time and expiry. Grok `quse.details.has_grok_code_access` plus installed CLI/version and current model route is evidence; an account percentage alone is not. For Antigravity use its listed Gemini route and saved Google sign-in; strip ambient API keys to avoid accidentally selecting a separately billed route. Requested model remains distinct from a runtime-observed model.
3. Fetch fresh quse at each actual provider launch, not from the five-minute metrics cache. Fail closed for query failure, malformed/unknown balance, `limit_reached` or exhausted relevant window. For OpenAI Codex, any available relevant window <=15% remaining blocks, unavailable windows are not zeros, and all windows unknown blocks. Use the real experiment `scripts/launch-codex.sh`; the wrapper's own gate rechecks. Copilot is excluded; Claude/Codex are sparse; no automatic reset redemption or purchases.
4. Evaluate exact model health, retry/backoff and required task capability. A broken route with abundant account quota is ineligible. A provider error must not cause a blind loop or a replay of a still-running writer. Reevaluate all eligible routes for the next attempt after confirmed failure and preserved evidence.
5. Reserve host capacity and ownership atomically in one durable store. Every scheduler using a different store is outside this guarantee. Read host memory and actual target/scratch filesystem; cap worker at 1500MiB, retain at least 10GiB MemAvailable after conservative reservations and at least 50GiB plus 512MiB spike on each relevant mount. This conservative GiB interpretation is stricter than a decimal 50GB floor. `/tmp` had ~32GiB and failed; owned root `.local/tmp` had ~62GiB and passed. Nonparticipating host processes can still consume resources after admission; cgroup limits and runtime failures must remain visible.

## Reset urgency, task fit and random choice

Use a bounded, auditable positive weight only after eligibility. A concrete candidate policy is `fit * health * preference * headroom * (1 + 2 * urgency)`, with `headroom = max(0.05, bottleneck_remaining/100)` and `urgency = max_known_window((remaining/100) * clamp((24-hours_to_reset)/24, 0, 1))`. The reset multiplier lies in [1,3]; missing or stale reset timestamps add no urgency. Long-window bottlenecks and task fit remain factors. This is a candidate formula to challenge empirically, not a measured optimal scheduler or a token budget.

Grok/ZAI get a modest preference when useful allowance risks expiring. Short rolling windows are not banked tokens that literally expire, and waiting until their reset is not the goal. Healthy Antigravity remains available. Weight sharing across duplicate model routes must not multiply one account's chance by the number of configured aliases. Record eligible list, rejection reasons, weights/probabilities, selected route and randomness provenance. Randomness cannot make an ineligible route eligible and must not ignore an explicit model requirement. Judge ranking by accepted useful outcomes per task, errors/retries and elapsed time; never by fabricated cost savings or percentage consumed.

## Durable launch and evidence semantics

Create a run/reservation before calling aplexer. Use deterministic unique tags, recorded launch intent, boot ID and session UUID; PID alone is inadequate because it is reused. The actual wrapper must call native `whoami`, matching expected workspace/tag, without forged environment or sender identity. Parent/child relationship belongs in the durable task record and actual native launch metadata.

If a launch call times out or its response is ambiguous, keep `launch-uncertain` and its ownership. Query the exact native session/tag and process identity; do not immediately repeat. A reboot proves prior processes died but does not prove the task failed or had no side effects. Preserve work and require owner reconciliation before a writer resumes. There is no universal exactly-once side-effect claim. A bounded retry requires a known terminal failure, released reservation and fresh admission. The time limit alone never proves lease ownership is safe to steal.

First action is evidence that the agent itself ran a tool in the assigned context and wrote meaningful structured progress; the wrapper's started file or `touch` is insufficient. Existing artifacts must not satisfy a new run. Distinguish `starting`, `running`, missing/invalid first evidence, `stalled`, failed, `completed-awaiting-review` and accepted. An uncertain spawn is different from a confirmed-running agent that has not produced evidence. Exit zero is not accepted output. Acceptance records reviewer identity and concrete result/test evidence.

## Analytics and completion criteria

Retain private provider observations separately from run-native tokens. Usage unknown is null, not zero; percentages are not tokens or money. Native cached/reasoning categories have provider-specific subset rules. Deduplicate by provider/native conversation/event; avoid adding parent-inclusive and child-inclusive streams twice. Historical hourly reports must disclose coverage/gaps and use actual observations, never backfill simulated 24-hour activity. File/commit/process counts do not establish accepted outcomes.

Before claiming v0.1 useful: pass real quota/admission/idempotency/path-overlap/ambiguity negative tests, run one genuinely useful task through the CLI with native identity and first action, verify result and review, push task and canonical SHA through Agent Branches, mirror exact GitHub main and restore, publish private projection for dashboard, and give head a concrete next task with its dependency/trigger. Unsupported routes, stale entitlements, incomplete telemetry and unreconciled runs remain visible.
